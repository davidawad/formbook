# Contributing to formbook

formbook is an open collection of court-filing templates in Typst, one folder per court and document type. Work is split into small units (one court, one document type), listed in `data/worklist.json`. Anyone can take one: no coordination with the maintainers beyond this repo.

## Point your agent here

Paste this into Claude Code, Codex, or any agent with a shell, git and (optionally) gh:

> Clone github.com/davidawad/formbook and read CONTRIBUTING.md and AGENTS.md. Run `sh tools/bootstrap.sh`, then `sh tools/contribute.sh pick`. Claim the unit it gives you with `sh tools/contribute.sh claim <id>`, do exactly what `sh tools/contribute.sh brief <id>` says inside the claimed worktree, make `sh tools/contribute.sh verify <id>` pass, then `sh tools/contribute.sh submit <id>`. Use only public court records, record every source URL, and look at every rendered page before submitting. If you are blocked on a decision only a human can make, stop and say so in the PR.

That is the whole loop. The rest of this file explains it.

## Toolchain

`sh tools/bootstrap.sh` installs the pinned toolchain (typst, poppler, imagemagick, gawk, jq, yq, pandoc, tectonic) into `~/.local/share/formbook/env` without root, then `export PATH="$HOME/.local/share/formbook/env/bin:$PATH"`. Fonts and typst packages are vendored. You also need `git`; `gh` is optional but makes claiming and submitting automatic. The contribution tools themselves are POSIX sh and jq. No Python.

## The loop

| Step | Command | Needs push access? |
|---|---|---|
| Pick | `sh tools/contribute.sh pick [--seed N] [--kind K] [--priority P]` | no |
| Claim | `sh tools/contribute.sh claim <id>` | write access, or use the fork workflow below |
| Do | `sh tools/contribute.sh brief <id>` prints the exact task | no |
| Verify | `sh tools/contribute.sh verify <id>` | no |
| Submit | `sh tools/contribute.sh submit <id>` | write access, or fork |

**Work units.** `data/worklist.json` lists every open unit as `{id, kind, alias, court_path, doctype, priority, status, note}`. The id is `<court alias>.<doctype>`, for example `ca1.amicus-brief`. It is regenerated by `sh tools/worklist.sh` from the tree (`data/index.json`, the vocabulary in `data/doctypes.json`, and what exists under `courts/`); contributors do not edit it, maintainers regenerate it after merges. Kinds:

| Kind | Meaning | Priority |
|---|---|---|
| `new-template` | A core document type for this court level has no working template yet (no folder, or a folder without a typst template) | high |
| `add-exemplar` | A template exists but no filed exemplar PDF (README says BLOCKED: no exemplar) | high |
| `new-doctype` | An extended, common filing for this court level (motions, oppositions, replies, petitions, notices) has no folder | normal |
| `deepen` | The template works, but its sample is shorter than a realistic filing, so layout under load is untested | low |

**Picking.** `pick` takes the best priority class that still has unclaimed units and chooses one pseudo-randomly. The default seed mixes the time, hostname, `$RANDOM` and the process id, so parallel contributors spread out; `--seed N` reproduces a pick (given the same claims). Units whose branch `contrib/<id>`, or whose whole court (branch `court/<alias>`), is already taken, or that have an open PR from a `contrib/<id>` branch, are skipped. Taking the unit you are told to take, rather than the one you like, is what keeps duplicate work low.

**Claiming.** A claim is the atomic creation of the remote branch `contrib/<id>` from `origin/master` (`git push --force-with-lease=<ref>:`, which fails if the branch exists), the same mechanism as `tools/claim.sh` for whole courts. If it fails, someone else has the unit; pick again. `claim <id> --dry-run` shows what would happen and pushes nothing. It creates a worktree at `.worktrees/<id>`; work only there.

**Without write access (fork workflow).** `claim` detects a rejected push and falls back to: fork the repo (`gh repo fork`), push `contrib/<id>` to your fork, and open a **draft PR** titled `claim(<id>)`. The draft PR is the claim: `pick` skips any unit with an open PR from a `contrib/<id>` branch, and `submit` later fills in that same PR and marks it ready. Why a draft PR and not an issue comment: it is machine-checkable from a branch name with one `gh pr list` call, it needs no parsing of free text and no maintainer, it is the same namespace as write-access claims, and it becomes the real PR, so there is no second step to forget. The limit: it is not atomic across forks, so two contributors can claim within the same minute; the earlier PR keeps the unit and the other should pick again. Without `gh`, create the fork and the draft PR by hand with the same branch and title.

**Abandoning.** Delete your branch or close your PR; the unit is open again. Say what blocked you.

## Quality bar

Summarised here; the full text is in [AGENTS.md](AGENTS.md) and [docs/EVAL-LOOP.md](docs/EVAL-LOOP.md), which win if they disagree.

- Tier 1, the court's mandated form (font and size, margins, spacing, length limits, required sections, certificates, e-filing rules), must be perfect and traceable to a cited rule. Tier 2, professional convention (cover, TOC and TOA, headings, caption, signature block), must look professional, judged against exemplars from different filers. Tier 3, one filer's style, is not chased.
- Templates are rule-driven and content-agnostic: no case-specific text, no coordinates measured off a filed PDF, no forced line breaks tuned to one document, no system fonts (compile only through `tools/render.sh`, which treats every typst warning as a failure).
- Look at every rendered page against the exemplar (`just overlay <folder>`; overlays land in the gitignored `.overlay/` and are not committed). Never claim a page was reviewed that you did not look at.
- Never set `"status": "done"` in a `court.json`. Do not edit other courts, `tools/`, `docs/`, `data/` or any generated tracker file in a unit PR; one PR is one folder.
- A folder is complete when it has `README.md`, `typst/main.typ` plus a template file, at least one `usage/SAMPLE-<stem>-<id>.pdf` with `usage/SOURCE.md`, at least one `usage/INPUT-<stem>-<id>.md` with its `usage/OUTPUT-<stem>-<id>.typst.pdf`. `<stem>` is `<court alias>-<doctype>`; `<id>` is lowercase `[a-z0-9]+`, no hyphens (see docs/EVAL-LOOP.md, "Folder layout"). `just lint` checks the names. Copy `courts/first-circuit/court-of-appeals/opening-brief/`.

## How verification works

`sh tools/contribute.sh verify <id>` is the mechanical floor. It fails if:

1. the folder layout above is incomplete, or `SOURCE.md` does not describe every exemplar PDF with a URL;
2. any `usage/INPUT-*.md` does not render through `tools/render.sh` (any typst warning fails), or its `usage/OUTPUT-*.typst.pdf` is not committed;
3. for a `deepen` unit, the longest output is shorter than the doc type's `min_pages` (`data/doctypes.json`);
4. `typst/` contains text copied from a sample's frontmatter (case numbers, party names, addresses) or prose, or a docket number;
5. any file outside the unit's folder changed relative to `origin/master`, or a `court.json` changed.

Passing means the unit is shaped and renders correctly; it does not mean the layout is right. That is the maintainers' review. `submit` reruns `verify` and pastes its output into the PR. `.github/workflows/contribute-verify.yml` reruns it on every PR, but it only runs once a maintainer enables GitHub Actions for the repo.

## How maintainers review and merge

A maintainer reads the PR body (verify output, exemplar sources, the open tier-2 findings you listed), renders the template against the exemplar, and spot-checks pages. Merging is by a maintainer only, never by the author. After merging, a maintainer runs `sh tools/worklist.sh` and `sh tools/tracker.sh` and commits the regenerated files, so unit PRs never conflict on shared files. Court `status: done` is set by the maintainer by hand. Expect changes requested for tier 1 problems; tier 3 differences are accepted and logged.

## Licensing and sources of exemplars

- Exemplars must be public court records: filings from a public docket or archive (CourtListener RECAP, the court's own site, a state e-filing portal open to the public). No sealed, restricted, private or client documents. Do not include filings that contain unredacted personal data the court would have required redacted.
- Record the exact source URL, filer, case, docket number, date filed and date retrieved for every exemplar in that folder's `usage/SOURCE.md`. A PR whose exemplar has no source URL fails verification.
- Rules text, templates and tools you write are contributed under the repository's license, the GNU GPL v3.0 ([LICENSE](LICENSE)). Quote court rules briefly and cite them; do not paste large copyrighted commentary.
- Disclose substantial AI assistance in the PR body (the template has a line for it). You are responsible for what your agent submits.

## Changing the tools or the vocabulary

Changes to `tools/`, `data/doctypes.json` (the document-type vocabulary per court level) or this file are infrastructure work, not unit work. Open a normal PR describing the change and run `sh tools/worklist.sh --check` to confirm `data/worklist.json` is current.
